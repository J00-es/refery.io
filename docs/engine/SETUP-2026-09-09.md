# Refery engine setup and validation

Prepared against application commit `d3a2ece` and the actual scheduled worker,
`J00-es/refery-automation` commit `8b89133`. All changes are in isolated local
branches. Nothing in this package has been deployed, applied to production,
pushed, or used to contact a candidate or company.

## What is implemented

- The actual GitHub Actions worker now has one concurrency group, a database
  contract check before writes, and pinned tested Python dependencies.
- Python model calls, including manual embedding helpers, reserve against the
  same engine budget as the app. Missing/refused reservations stop dispatch.
  The SDK makes no automatic retries. Timeouts retain their reservation;
  invalid generated content is charged before parsing. The old panel entry
  point explains the supported queue replacement and cannot grade anyone.
- The nightly process queues missing assessments for the application's leased
  panel worker. It no longer runs its own grading logic or accepts a match
  based on a similarity threshold.
- Each nightly candidate transaction searches the current open job board and
  commits assessments, review proposals and progress together. A failed write
  rolls back progress; restarting the same UTC-date run resumes it. Empty
  results are recorded. Candidate grades and pipeline creation timestamps are
  not eligibility gates or progress cursors. Proposal ownership is preserved.
- Parsed résumé claims can be stored with exact source paths, original
  snapshots and matching raw spans. They remain `self_reported`; an AI parser
  is not independent verification. Concurrent source changes refuse the write.
- Versioned scorecard drafts preserve job requirements and published hiring
  manager briefs. The importer cannot confirm hard requirements. The first
  6–12 month outcomes, priorities and acceptable substitutes require a hiring
  manager's input. Family-specific evidence anchors are included.
- A separate capability-text builder and shadow vector columns/backfill are
  ready. Active embeddings stay unchanged until retrieval quality is measured.
  The shadow builder omits identity fields, school and employer names, grades,
  and structured logistics. It is not an anonymization guarantee for free text.
- A synthetic benchmark can use the existing OpenAI account directly, with a
  durable, separate $5 cap before the production ledger exists. Its $0.41529342
  estimated token cost has an idempotent reconciliation SQL file to import
  into the shared envelope after the migrations.
- Reapplying migration 04 now excludes already-metered panels and bench runs
  from the legacy-cost import, and creates/locks the month before importing.

These are executable foundations and worker changes. Human-confirmed scorecards,
production capability-vector promotion and proven hiring quality are not claimed.

## Validation and practical limits

- App unit tests: 88 passing tests across 7 files.
- Actual worker: 12 passing tests, with the installed Python OpenAI SDK.
- PostgreSQL 17.6: separate real connections exercise claims, lease expiry,
  reruns, dormant/human decisions, budgets, outbox ownership, transactional
  matching, evidence, scorecards and repeat cost imports. See the JSON report
  for the exact scenarios. The fixture replaces vector retrieval; it does not
  validate HNSW, hosted Supabase permissions, or the full production schema.
- `pnpm build` passed. The repository already bypasses TypeScript errors during
  builds. Independent checking found the same 90 pre-existing diagnostics at
  `d3a2ece` and on this branch. Building generates three more checks against
  unchanged agreement routes; those also reproduce against the base code with
  the same generated types. No changed engine file adds a diagnostic.
- Read-only candidate preview: all 337 records examined; 17 lack enough usable
  capability text. A 100-job preview found 22 thin records. Such records need
  better source material; they must not be assigned fabricated capabilities.
- The human evaluation packet is unlabelled. It contains 120 candidates and
  360 sampled pairs, prepared with zero retrieval errors. Legacy grades are used only
  to diversify sampling and are withheld from reviewer labels. Existing vector
  retrieval plus a random job supplies candidates for judgment; it is not a
  complete relevance census of the board. Failures and sampling are recorded.
- `engine:evaluate` refuses to treat absent labels as validation. It reports
  precision only for fully judged top-three results, and recall only within
  the judged pool. It never authorizes model promotion automatically.
- A deliberately failed database run exits with status 1 after cleanup. Each
  run uses a free local port, so simultaneous test processes cannot steal the
  same port and hang during shutdown.

## What the live model benchmark actually says

Eight synthetic candidates, three synthetic seats, the production panel prompt,
low reasoning effort, and 32 real API generations:

| Route | Automatic fixture checks | Cost for 8 cases | Average per case |
|---|---:|---:|---:|
| GPT-5.6 Luna | 7/8 | $0.011790 | $0.001474 |
| GPT-5.4 mini | 8/8 | $0.045322 | $0.005665 |
| GPT-5.6 Terra | 7/8 | $0.143687 | $0.017961 |
| GPT-5.6 Sol | 6/8 | $0.214494 | $0.026812 |

All 32 returned structured output. The expectations include subjective fixture
assumptions about grades and screening decisions. Treat the counts as diagnostic
tests, not independently established model rankings. The fixture résumés are
short and most calls got prompt-cache hits. Costs use reported tokens and the
reviewed price register, not an invoice reconciliation. Stored responses were
retrieved to preserve full outputs without paying for another generation.

GPT-5.4 mini is the best next panel pilot from this limited test. Keep Luna for
low-risk extraction/triage trials; consider mini for detailed matching only
after a separate pair benchmark. Terra or Sol should earn an exception route
on examples where they improve a measured outcome. This run did not compare
the incumbent Anthropic models and did not benchmark transcript extraction or
real candidate/job matching. Production model defaults and route approval flags
remain unchanged.

For the under-$100 target, retain the shared $95 hard stop, $85 deferral and $70
alert, and include benchmark/backfill charges in the envelope. Do not extrapolate
short synthetic cached calls into a guarantee for long real documents. Measure
per-task tokens, cache use, failures and exceptions before increasing volume.

## Activation order

1. Review/apply the application patch on top of `d3a2ece`; review the worker patch
   against the actual `refery-automation` repository, not a disconnected local
   `C:\\scripts` copy. Keep the old schedule disabled while changing the database
   and worker together: the old worker does not implement the new contract.
2. In a disposable Supabase environment with the real schema and pgvector,
   apply release-1 SQL files 01, 02, 03, 04 in order, then
   `supabase/migrations/20260909105010_engine_evidence_and_complete_matching.sql`.
   The original release-1 scripts are not Supabase CLI migration-history entries;
   do not blindly run `supabase db push` and skip those prerequisites.
3. Run policy parity, hosted role/permission checks, full retrieval tests and
   a paused-notification end-to-end worker run. Confirm proposals appear under
   the correct owner, humans remain excluded, and retries do not duplicate work.
4. Review the resulting migration/backfill plan before production activation.
   Apply the same migration order, then the benchmark reconciliation SQL. Keep
   all outbound sends disabled during verification. Deploy the application and
   the actual scheduled worker together, check `engine_worker_contract`, and
   resume the schedule only after a successful controlled run.
5. Preview evidence with `pnpm engine:evidence -- --limit 100` and for jobs add
   `--kind job --department Engineering --family engineering` when that exact
   department is appropriate. The general `other` draft is the safe default. `--apply` writes facts
   or drafts. `--apply --embed-shadow` also buys shadow embeddings through the
   shared ledger. Resume using the last successful `--after` ID in the report.
   `ENGINE_EVIDENCE_ENABLED=1` opts panel runs into mandatory fact persistence;
   enable only after migration 05 is verified.
6. Human reviewers fill the private evaluation packet and confirm real role
   requirements. Add pooled candidates from lexical and shadow vector routes
   before claiming retrieval recall. Separate development and held-out people.
   Check evidence correctness, logistics, refusals, prompt injection, known
   exclusions and meaningful hiring outcomes. Do not ask Claude to invent
   human labels or silently convert legacy opinions into verified decisions.
7. After provider/account review and these tests, explicitly approve a candidate
   data route and configure `DESK_PANEL_MODEL`/`DESK_BENCH_MODEL` for the pilot.
   Do not replace all roles with a new model based on these eight fixtures.
